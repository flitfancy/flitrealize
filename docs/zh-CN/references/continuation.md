# 跨对话续接与状态归属

续接项目或更新当前状态时读取本参考。

## 使用唯一读取顺序

1. 确认精确项目根目录，不从同级项目借用事实。
2. 先读 `CURRENT_HANDOFF.md`，取得稳定身份、版本、决策、受保护制品、风险和当前证据状态。
3. 只有 `BATTLE_LOG.md` 命名了活动且不稳定的子系统时，才随后读取。它只能覆盖该子系统结论，不能覆盖项目身份或范围。
4. 验证所列路径和身份元数据；记录漂移并对账拥有该事实的源，不能相信文件名或回忆。

日期总结只用于理由或冲突解决。把新请求与恢复出的范围比较；大范围修改前先解决与冻结决策的冲突。

## 使用正确的权威链

```text
当前意图与授权：
当前用户明确指令 > 当前项目状态 > 旧总结

制品事实：
实时 EDA 回读 > 匹配的已保存源/capture > 直接 battle 证据
> 当前 handoff > 旧总结 > 回忆
```

用户报告可以改变目标或授权；技术主张仍需相应事实源。过期或不安全判定立即生效，只有获准写入项目状态后才会跨对话持久。

## handoff 保存当前状态，不保存历史

每个项目根目录只有一个简洁的 `CURRENT_HANDOFF.md`。分开记录已确认决策、带限定词的已验证事实和假设。只保留当前身份、范围、版本、证据、风险、权威/过期制品和下一步；时间线与被否决方案移入日期总结。项目允许时，目标约为 40–80 行。

使用紧凑结构：

```markdown
# <项目> current handoff
Updated: <时间戳与时区>
Project root: <绝对路径>

## 身份、目标与范围
## 已确认决策
## 已验证事实与证据状态
## 假设、风险与阻塞
## 权威与过期制品
## 下一步与续接说明
```

指定一个带成功判据的主要下一步；允许最多两个不会改变或使主路径失效的独立并行动作。

稳定且实质性的变化后更新，例如阶段转换、重大回滚、新下单候选、大范围变更或已解决故障。不要粘贴聊天记录或不稳定实验细节。

## battle log 只用于活动故障

只有一个子系统结论会随着重复聚焦实验变化时，才创建 `BATTLE_LOG.md`。它记录子系统边界、当前假设/结论、直接证据，以及一个带停止条件的下一实验。普通实现、一次性故障或已完成工作不进入其中。

结论稳定后，把带证据链接的简短结果合并进 handoff，并在授权范围内归档或删除 battle log。

## 保持制品归属可见

| 状态 | 常见拥有者 |
| --- | --- |
| 需求与架构 | 版本化需求/设计制品 |
| 原理图意图 | 契约、BOM、引脚/网络和测试点表 |
| PCB 意图 | PCB 契约和布局/布线证据 |
| 制造候选 | 版本化 manifest 与 Gerber/钻孔/装配包 |
| 上电 | 验证报告和原始日志 |
| 项目持续状态 | 当前 handoff 与可选活动 battle log |

重新生成前查询拥有该事实的制品。文件存在或名字正确都不能证明它匹配活动版本。
