# 2.1 原理图设计与 Contract

需求、架构和主要器件已经基本确定，需要建立原理图连接、检查设计或准备进入 EDA 时读取本参考。

本阶段把设计转换成准确、可检查的电路。机器意图保存在 Contract，人类可读设计进入 `CURRENT_HANDOFF.md` 的 2.x 章节。

## 输入

开始原理图前，读取当前任务需要的：

- 产品目标和明确非目标；
- 功能架构；
- 电源树；
- 外部接口；
- 主要工作条件；
- 已确认器件和当前候选；
- 关键计算；
- 准备在样机阶段确认的问题。

问题会改变功能块、电源结构、主要接口或关键器件路线时，先更新 1.x 设计内容。

## 建立机器 Contract

使用：

```text
design/SCHEMATIC_CONTRACT.v1.json
```

保存可移植原理图意图。格式由：

```text
<skill>/schemas/schematic-contract.v1.schema.json
```

定义。

Contract 不依赖具体 EDA，也不保存画布坐标和显示样式。

按项目实际需要记录：

- 功能块；
- 电源域和主要电源轨；
- 元件作用；
- `exact` 器件的制造商、MPN、后缀和封装；
- `generic` 器件的数值、额定值、公差、封装和允许范围；
- 接口方向和电压域；
- 语义引脚；
- 引脚到网络的连接；
- 上拉、下拉、使能和默认状态；
- NC、DNC、散热焊盘和必须连接的裸露焊盘；
- 保护和故障关断路径；
- 测试点；
- 当前样机确认项。

Contract 只保存当前设计，不保存讨论过程和被否决方案。

## 引脚事实

```text
制造商数据手册
    → 器件原始引脚和电气事实

Schematic Contract
    → 当前项目怎样使用这些引脚

EDA Provider Binding
    → 当前 EDA 符号怎样对应这些引脚

EDA 原理图回读
    → 实际画出的连接
```

Contract 使用稳定、易理解的语义引脚名称，例如：

```text
VIN
GND
SCL
SDA
EN
SW
FB
```

Provider 可以把语义引脚映射到原生符号引脚：

```json
{
  "bindings": {
    "easyedaPro": {
      "libraryUuid": "...",
      "deviceUuid": "...",
      "pinMap": {
        "VIN": ["1", "2"],
        "GND": ["3"]
      }
    }
  }
}
```

Binding 只负责 EDA 身份映射，不改变 Contract 中的电气设计。

器件身份、符号或引脚映射存在歧义时，先确认受影响器件，不根据名称相似、图形位置或搜索结果第一项推断。

## 引脚调整

默认引脚保持固定。

只有 MCU、FPGA 或其他明确支持复用的器件，才允许在 PCB 粗布局后调整尚未分配的可配置引脚：

- `fixed`：保持当前引脚；
- `unused_configurable_only`：只使用同一器件上尚未分配、并且已经确认支持目标功能的引脚。

目标是解决明显交叉、绕行、拥挤或过孔，不搜索全部排列。没有明显更好的候选时保持当前映射。

实际调整后同步更新 Contract、原理图、主文稿和受影响的固件接口。

## 初步 PCB 意图

原理图阶段为重要网络记录后续 PCB 需要的电气条件：

- 网络类别；
- 连续和峰值电流；
- 电压和允许压降；
- 开关节点或敏感模拟节点；
- 差分、阻抗或长度关系；
- 是否需要减少过孔、缩短路径或保持连续参考。

这些条件用于指导 PCB，不在原理图阶段固定最终线宽。实际线宽、间距、过孔和铺铜由层叠、铜厚、长度、散热和制造能力共同决定。

## 更新项目主文稿

把当前原理图设计整理进 2.x 章节。

### 电路分块

说明每个电路块的：

- 用途；
- 输入和输出；
- 主要器件；
- 与其他功能块的关系；
- 启动、关闭和故障行为。

### 元器件、引脚与网络

从 Contract 派生可读内容，例如：

```text
位号 | 器件作用 | 引脚 | 引脚功能 | 网络 | 默认状态 | 必连/NC/DNC
```

同时记录允许重新分配的未使用可配置引脚。

连接变化时先修改 Contract，再刷新主文稿中的人类视图。

### 关键计算

保留会影响器件、连接、额定值或样机测试的计算，例如：

- 电压和电流；
- 功耗和温升；
- 反馈与定时参数；
- 保护阈值；
- 元件降额；
- 当前设计余量。

### 测试点与样机确认项

记录：

- 测试点；
- 测试条件；
- 预期值；
- 当前需要样机确认的问题。

### EDA 实现状态

进入 EDA 后记录：

- 当前 Provider；
- 原理图源文件；
- 已经实现的范围；
- 尚未写入或尚未对账的内容；
- 当前 ERC/DRC 状态。

## 按功能检查

### 电源入口

检查输入范围、极性、连接器额定值、反接、浪涌、ESD、输入限流和返回路径。

### 稳压器与电源轨

检查输入输出范围、负载、压差、效率、损耗、温升、电感、电容、反馈、启动、关闭、使能默认状态和稳定性条件。

### 控制与默认状态

检查复位、主控未初始化、控制信号开路或失电、MOSFET 和驱动器关闭状态，以及保护和关断路径。

### 接口与电压域

检查方向、源宿关系、逻辑阈值、电平转换、上拉域、地址、热插拔、断线、ESD、误接和连接器针脚。

### 传感器与负载

检查推荐外围电路、输入输出范围、偏置、增益、滤波、启动、故障、裸露焊盘、NC、DNC 和校准节点。

### 器件与封装

检查准确身份、规格、封装、引脚、额定值、公差、采购身份和允许替代。

器件资料处理见 [1.2-parts.md](1.2-parts.md)。

## Contract 检查

完成 Contract 后运行：

```text
node <skill>/scripts/action-runner.mjs run \
  --action schematic-contract-audit \
  --input-file <schematic-contract.json>
```

它检查：

- JSON 结构；
- 元件、网络和功能块身份；
- 交叉引用；
- 引脚到网络的归属；
- NC 和 DNC；
- 电源域；
- 接口和差分关系；
- Provider Binding 边界。

Contract Audit 只证明结构和引用一致，不证明电路拓扑、器件能力、EDA 实现或实物功能。

## 进入 EDA

## 进入 EDA

准备把某个功能块写入 EDA 时，确认该范围内：

- 电路结构、器件、引脚和主要网络已经写入 Contract；
- 关键器件的身份、封装和引脚已经确认；
- `generic` 器件具有本次实现需要的规格和封装要求；
- 控制、保护和未连接引脚的状态已经明确；
- Contract Audit 没有影响本次写入的错误。

其他尚未确定的功能块继续保留在主文稿中，不阻止已经明确的部分进入 EDA。会改变本次连接的问题先留在原理图设计阶段解决；只能通过实物判断的问题转成样机测试。

使用 EasyEDA Pro 时读取：

[2.2-schematic-workflow.md](providers/easyeda-pro/2.2-schematic-workflow.md)

## 与 EDA 对账

EDA 写入后回读实际器件、引脚、网络、电源标识、未连接引脚、关键属性和保存状态。

Contract 表示设计意图，EDA 回读表示实际实现。两者不一致时，修正拥有错误事实的一侧。

ERC 用于发现当前规则能够识别的连接问题，不判断拓扑、额定值、保护行为和系统功能。

## 进入 PCB

进入 PCB 前确认：

- 当前原理图已经保存；
- 实际器件、引脚和网络已经与 Contract 对账；
- 未连接引脚和有意例外已经说明；
- 当前 ERC/DRC 问题已经处理；
- 剩余问题不会改变当前连接；
- 主文稿中的 2.x 章节和顶部当前交接已经更新。
