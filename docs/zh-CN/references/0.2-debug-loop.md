# 0.2 处理反复失败

本参考是 CURIOUS_MODE 的实验调试分支。

当同一个局部问题需要经过多轮观察、测量或修改才能判断时读取。普通实现、一次检查能够解决的失败，以及单纯的资料核验不需要读取。

## 进入调试循环

出现以下情况时，只对相关问题进入 CURIOUS_MODE：

- 实际结果与设计预期不一致；
- 已有资料、日志或测量结果互相冲突；
- 一次正常检查无法确定问题原因；
- 相似修改已经重复出现，但结果仍不稳定；
- 必须通过实验才能区分几种合理解释。

进入调试循环不会扩大当前任务范围。与问题无关的设计和已经确认的结论保持不变。

## 先整理当前事实

再次修改前，先明确：

- 实际观察到了什么；
- 哪些结果已经确认；
- 最近改变了什么；
- 当前有哪些合理解释；
- 哪个简单测试最能帮助判断。

优先使用已有报错、测量、日志、EDA 回读和实际文件。不要只根据预期结果推断当前状态。

如果现有证据已经足以确定原因，直接修复并返回 DEFAULT_MODE，不需要继续建立实验流程。

## 一次验证一个问题

选择能够排除至少一种合理解释的最小测试。

测试前说明：

- 准备改变或观察什么；
- 不同结果分别说明什么；
- 什么情况下停止或恢复原状。

测试后根据实际结果更新判断，再决定下一步。

没有得到新信息时，不要继续制作相似修改、反复运行同一流程，或者同时改变多个可能原因。

如果问题只影响一个局部，不需要每次重新检查完整 BOM、原理图、PCB 或制造文件。只有发现问题可能影响其他部分时，才扩大检查范围。

## 需要跨对话时保存临时记录

只有一个未解决问题需要经过多轮实验时，才创建 `DEBUG_NOTES.md`。

它只记录当前调试所需的信息：

```markdown
# 问题与影响范围

# 已观察到的事实

# 当前判断

# 下一项测试

# 需要恢复或保留的修改
```

`CURRENT_HANDOFF.md` 保存整个项目的当前状态；`DEBUG_NOTES.md` 只保存这个活动问题。

不需要为一次性失败、已经确认的问题或普通实现过程创建调试记录。

## 停止无效尝试

出现以下情况时，停止继续修改：

- 新尝试与之前没有实质区别；
- 当前工具无法观察需要判断的状态；
- 继续尝试只能增加变量，不能排除原因；
- 需要用户操作、实物测量或外部资料才能继续；
- 当前问题已经能够转化为明确的后续测试。

停止时保留已经确认的事实，说明当前缺少什么，并给出最小的下一项观察或测试。

不要为了保持工作进行而继续堆积补丁、脚本变体或临时绕过方案。

## EDA 调试

涉及 EDA 时，先确认当前文档、实际保存状态和最近一次修改结果，再按照当前 EDA Provider 的流程继续。

一次只保留一个准备继续使用的修改方案。确认方案无效后，再恢复、替换或生成下一版，避免多个实验版本同时存在而无法判断实际执行的是哪一个。

## 返回默认模式

出现以下任一结果后，结束本次调试循环并返回 DEFAULT_MODE：

- 问题原因已经确认；
- 已找到可以实施并验证的修复；
- 问题已经转化为明确的样机测试；
- 已确认必须等待用户操作、实物测量或外部资料；
- 继续尝试不会产生新的判断依据。

如果形成了稳定结论，把结果和必要证据简要写回 `CURRENT_HANDOFF.md`。

问题结束后，删除或归档 `DEBUG_NOTES.md`，不要让临时判断继续影响后续设计。
