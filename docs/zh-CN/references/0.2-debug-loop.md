# 0.2 处理反复失败

当同一个局部问题需要经过多轮观察、测量或修改才能判断时读取本参考。

普通实现、一次检查能够解决的失败，以及单纯的资料核验不需要进入调试循环。

## 进入调试

以下情况只对相关问题进入 CURIOUS_MODE：

- 实际结果与设计预期不一致；
- 资料、日志、测量或 EDA 回读互相冲突；
- 一次正常检查无法判断原因；
- 相似修改反复出现，但结果仍不稳定；
- 必须通过实验才能区分几种合理解释。

调试只处理当前问题。与它无关的设计和已经确认的结论保持不变。

## 整理当前事实

再次修改前，先明确：

- 实际观察到了什么；
- 哪些结果已经确认；
- 最近改变了什么；
- 当前有哪些合理解释；
- 哪个最小测试能够区分这些解释。

优先使用已有报错、测量、日志、EDA 回读和实际文件。现有证据已经足以确定原因时，直接修复并返回普通工作。

## 一次验证一个问题

选择能够排除至少一种合理解释的最小测试。

测试前说明：

- 准备改变或观察什么；
- 不同结果分别说明什么；
- 什么情况下停止或恢复原状。

测试后根据实际结果更新判断，再决定下一步。

没有获得新信息时，不继续制作相似修改，也不同时改变多个可能原因。

问题只影响局部时，不重复检查完整 BOM、原理图、PCB 或制造文件。发现影响范围扩大后，再检查相关部分。

## 保存活动问题

问题需要跨任务继续时，使用一个 `DEBUG_NOTES.md`：

```markdown
# 问题与影响范围

# 已观察到的事实

# 当前判断

# 下一项测试

# 需要恢复或保留的修改
```

它只保存当前实验需要的信息，不承担整个项目的交接。

## 停止无效尝试

出现以下情况时停止继续修改：

- 新尝试与之前没有实质区别；
- 当前工具无法观察需要判断的状态；
- 继续尝试只会增加变量；
- 需要用户操作、实物测量或外部资料；
- 当前问题已经能够转成明确的后续测试。

停止时保留已经确认的事实，并说明当前缺少什么以及下一项最小观察。

## EDA 调试

涉及 EDA 时，先确认当前文档、保存状态和最近一次写入结果，再使用当前 Provider 的对应流程。

一次只保留一个准备继续验证的方案。确认方案无效后，再恢复或替换，避免多个实验版本同时存在。

## 返回普通工作

出现以下结果后结束调试：

- 原因已经确认；
- 修复已经实施并验证；
- 问题已经转化为明确样机测试；
- 必须等待用户操作、实物测量或外部资料；
- 继续尝试不会产生新的判断依据。

稳定结论更新到 `CURRENT_HANDOFF.md` 中受影响的设计、PCB 或验证章节，并同步顶部当前交接。

问题结束后删除或归档 `DEBUG_NOTES.md`。
