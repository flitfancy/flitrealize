# 5.1 Prototype bring-up, testing, and revision

Read this reference when prototype hardware has arrived and the project needs first power, functional validation, fault isolation, or a revision decision.

Test objectives come from current requirements, design assumptions, and prototype checks left by schematic design.

## Prepare for power-up

Before applying power, confirm:

- board version and assembly state;
- input source, polarity, and range;
- main rails and expected voltages;
- normal startup current and a conservative current limit;
- default state of outputs, enables, and protection;
- important test points;
- functions and assumptions to verify;
- stop conditions for abnormal behavior.

Current limits and stop conditions come from the current design. When an exact value is unavailable, begin with a conservative value that permits safe startup and adjust from measurement.

A multimeter and current-limited supply are usually enough for basic bring-up. Use other instruments only when the current test needs them.

## Unpowered inspection

Before connecting power, inspect:

- part model, orientation, and polarity;
- connectors and jumpers;
- bridges, poor joints, debris, and damage;
- rework and unpopulated parts;
- obvious shorts from main rails to ground;
- distinction between input, output, and battery terminals.

Correct assembly, short-circuit, or polarity faults before applying power.

## First power-up

1. Disconnect unnecessary loads and high-energy actuators.
2. Set the correct input voltage and a conservative current limit.
3. Apply input and observe current.
4. Measure main rails.
5. Check for abnormal heating, smell, noise, or oscillation.
6. Confirm reset, enable, and output defaults.
7. Connect or enable other blocks gradually.
8. Observe current, voltage, and temperature after each change.

Stop when:

- input current is clearly above expectation;
- a rail has the wrong voltage or polarity;
- a part heats rapidly;
- protection cycles repeatedly;
- unexplained oscillation, sound, or smell appears.

Preserve the observation and measurements before deciding whether the cause is assembly, circuit, firmware, or test conditions.

## Functional testing

After basic power is correct, test the current requirements:

- input and output ranges;
- interface communication;
- startup, reset, and enable;
- sensors, actuators, and loads;
- operating modes;
- output accuracy, ripple, and temperature rise;
- load changes and startup transients;
- power transitions and recovery;
- required protection or fault behavior.

Test normal operation before boundaries and faults. Fault testing covers only conditions the design can safely tolerate and that the current objective actually requires.

Test duration and repetition follow the current objective and failure timescale.

## Record results

Record enough to support the current judgment:

```text
Test | Condition | Expected | Measured | Result | Evidence
```

Also record board version, assembly or rework state, input conditions, firmware version, and instrument settings when they affect reproducibility.

Keep ordinary passing results short. Preserve enough measurements, waveforms, photographs, or logs to reproduce abnormal behavior.

Distinguish:

- meets the requirement under the tested condition;
- works with a known limitation;
- disagrees with expectation;
- cannot be determined under the current condition.

A result covers only the tested board, condition, and function.

## Handle faults

First classify the issue as:

- assembly or soldering;
- schematic or part;
- PCB, return path, thermal, or mechanical;
- firmware or configuration;
- test method or external condition.

When the cause is clear, correct it and retest. When the same issue needs multiple experiments, read [0.2-debug-loop.md](0.2-debug-loop.md).

Change one main variable per experiment.

## Decide on a revision

A revision follows physical evidence and the product objective, for example:

- a function or safety requirement is not met;
- part, pin, package, or connection is wrong;
- power, signal, thermal, or mechanical margin is insufficient;
- manufacturing, assembly, test, or service has an actual problem;
- a current limitation prevents the product objective.

For a revision, record:

- the observed problem;
- evidence supporting the judgment;
- design objects to change;
- expected effect of the change;
- tests to repeat on the next revision.

Update the manuscript section and machine artifact that own the affected stage.

## Update the project manuscript

Under section 5.x, record:

- board version and assembly state;
- test conditions;
- measured results;
- current limitations;
- faults and evidence entry points;
- accepted conclusions;
- rework, continued testing, or revision decision.

Update the current handoff at the top as well.

When results change requirements, parts, schematic, or PCB, update those sections too. Do not leave a new design conclusion only in the test record.

## Finish this stage

The project should be able to state:

- which core functions were physically verified;
- tested conditions and limitations;
- which issues need rework, more experiment, or revision;
- whether the next step is more testing, design change, or completion of the current prototype objective.

Read [6.1-production-release.md](6.1-production-release.md) only when the user explicitly requests repeat production, volume PCBA, a formal version, or a release conclusion.
