# 1.1 Requirements and architecture

Read this reference when starting a hardware design or when an existing project changes its major function, power structure, external interfaces, or core part strategy.

This stage decides what to build and how its blocks work together. Exact component connections and EDA implementation belong to later stages.

## Start a new project

For `NEW_PROJECT`, use the exact root the user provided and create only the files needed by the current stage. Add `CURRENT_HANDOFF.md` only when the work must continue across tasks. Do not read or inherit state from sibling projects unless the user explicitly asks to reuse something.

## Define the goal and boundary

Capture what the product actually needs:

- use case and primary functions;
- inputs, outputs, and external interfaces;
- power sources, operating range, and major loads;
- size, enclosure, environment, and mounting;
- cost, quantity, inventory, and sourcing constraints;
- explicit non-goals.

Ask only questions that change architecture, major parts, or acceptance. A normal gap that can be resolved safely on the prototype may become an explicit test instead of blocking design for documentation completeness.

## Build the functional block diagram

Split the product into blocks that can be described and tested independently.

For each block, state:

- purpose;
- inputs and outputs;
- power source;
- interfaces to other blocks;
- startup, shutdown, and default state;
- how major faults affect other blocks;
- the simplest useful test.

Stop at the detail needed for architecture and schematic work. Do not expand every part and pin yet.

## Build the power tree

Show each source, conversion stage, and major consumer. Record what the current design needs:

- nominal, minimum, and maximum voltage;
- continuous and peak current;
- startup order;
- enable and shutdown conditions;
- reverse input, surge, short-circuit, overcurrent, and undervoltage behavior;
- high-current and switching nodes that may constrain the PCB.

Average power does not replace peak, startup, or fault conditions. Calculate enough to choose the architecture and major parts without inventing precision for details that are still open.

## Define interfaces

For important external and inter-block interfaces, record:

- signal or power direction;
- protocol and voltage domain;
- connector or cable conditions;
- hot-plug, disconnect, and misconnection behavior;
- default state and recovery;
- firmware, mechanical, or enclosure dependencies.

Stabilize external interfaces before optimizing the implementation. When external behavior changes, update the architecture before changing parts or schematic details.

## Define defaults and faults

For paths that affect product function or safety, state:

- state during power-up and reset;
- state before a controller is initialized;
- state when a control signal is open or unpowered;
- behavior under weak input, overload, or overtemperature;
- recovery after protection acts;
- what the user can observe or measure.

When available evidence cannot resolve a protection, isolation, or fault-shutdown question, enter CURIOUS_MODE only for that question.

## Identify cross-domain conditions

Mark design decisions that depend on:

- firmware and startup timing;
- cooling and sustained load;
- acoustic, optical, or sensor installation;
- enclosure, harness, or connector geometry;
- transient or fault behavior of several parts together.

Proceed when normal sources and calculations support the decision. If only hardware can answer it, convert it into a prototype test with defined conditions and observations.

## Enter part and schematic work

This stage is complete when the project can answer:

- what the product will do now;
- which blocks provide it;
- how power flows;
- how major interfaces connect;
- what the default and fault states are;
- which questions affect parts or connectivity and which remain prototype tests.

Then use [1.2-parts.md](1.2-parts.md) for the major parts and [2.1-schematic-contract.md](2.1-schematic-contract.md) for exact pins and nets.
