# 0.2 Repeated-failure debugging

This reference is the experimental debugging branch of CURIOUS_MODE.

Use it when one local problem needs repeated observation, measurement, or modification before it can be understood. Do not load it for ordinary implementation, a failure solved by one normal check, or a simple source verification.

## Enter the loop

Use CURIOUS_MODE only for the affected problem when:

- actual behavior disagrees with the design expectation;
- available sources, logs, or measurements conflict;
- one ordinary check cannot identify the cause;
- similar changes have been tried but the result remains unstable;
- an experiment is required to distinguish reasonable explanations.

The loop does not expand task scope. Unrelated design and accepted conclusions remain unchanged.

## Start from current facts

Before changing anything again, state:

- what was actually observed;
- which results are already confirmed;
- what changed most recently;
- which explanations remain plausible;
- which simple test would distinguish them.

Prefer existing errors, measurements, logs, EDA reads, and actual files over inference from expected behavior.

If the existing evidence already identifies the cause, fix it and return to DEFAULT_MODE.

## Test one question at a time

Choose the smallest test that eliminates at least one plausible explanation.

Before the test, state:

- what will change or be observed;
- what each result would mean;
- when to stop or restore the prior state.

Use the result to update the conclusion before choosing another test.

Do not keep making similar changes, repeating the same flow, or changing several possible causes at once when no new information is produced.

If the issue is local, do not rerun the complete BOM, schematic, PCB, manufacturing, ERC, or DRC review each time. Expand only when evidence shows a wider effect.

## Save temporary notes only when needed

Create `DEBUG_NOTES.md` only when one unresolved problem must continue across several experiments or tasks.

```markdown
# Problem and affected scope
# Observed facts
# Current conclusion
# Next test
# Changes to preserve or restore
```

`CURRENT_HANDOFF.md` owns overall project state. `DEBUG_NOTES.md` owns only the active problem.

Do not create it for a one-off failure, an understood issue, or normal implementation work.

## Stop uninformative attempts

Stop changing things when:

- the new attempt is not materially different from an earlier one;
- current tools cannot observe the deciding state;
- another attempt would add variables without eliminating a cause;
- progress requires a user action, physical measurement, or external source;
- the issue can now be expressed as a precise later test.

Preserve confirmed facts, explain what is missing, and give the smallest next observation or test. Do not maintain momentum by accumulating patches, script variants, or temporary workarounds.

## EDA debugging

For EDA work, confirm the current document, saved state, and result of the latest change before continuing with the active Provider flow.

Keep only one modification plan intended for continued use. Once it is rejected, restore or replace it before generating another so the active experiment remains clear.

## Return to DEFAULT_MODE

End the loop when:

- the cause is known;
- a fix can be implemented and verified;
- the issue has become a precise prototype test;
- progress must wait for user action, physical measurement, or an external source;
- another attempt would not provide new evidence.

If the result changes stable project state, write the short conclusion and necessary evidence pointer back to `CURRENT_HANDOFF.md`. Then archive or delete `DEBUG_NOTES.md` so temporary reasoning does not govern later work.
