# 0.1 一份项目主文稿与续接

新建、继续或交接项目时使用。全流程只维护一份 `CURRENT_HANDOFF.md`：既能让人读懂设计，也能让下一次任务找到当前入口，不为原理图、PCB 等阶段分别新建交接文件。

## 开始与续接

- 新项目先确认用户指定的根目录，从已知目标、需求、器件条件和下一步开始，不继承同级项目的设计状态。
- 已有主文稿时，先读顶部交接和本次相关章节，再读拥有事实的机器文件；不每次全盘扫描。
- 主文稿缺失时，从本项目需求、设计、EDA、制造和测试制品恢复。缺少依据的内容标明未决，不凭旧文件名补全。纯查看任务只报告缺口，不自动创建文件。
- 当前用户请求决定范围与授权，旧交接中的“下一步”不是新的写入授权。

## 正文结构

按项目进展逐步填写，保留稳定章节和目录链接。文档可以大，不为缩短篇幅拆散人类需要一起理解的设计。

```markdown
# <项目名称>

Updated: <时间>
Project root: <绝对路径>

## 0. 当前交接

当前阶段: <对应阶段章节标题，不含编号；尚未明确时写“待明确”>

ViewState: <当前正在做什么、主要变化或卡点，以及最小有用下一步的简短说明>

- 当前目标、阶段与版本：
- 已完成和仍未验证的范围：
- 本次入口、输入及证据：
- 当前限制或阻塞：
- 最小有用下一步：

## 目录

## 1. 需求、架构与器件

### 1.1 设计意图、使用场景与验收目标
### 1.2 需求、非目标与设计限制
### 1.3 功能框图、电源树与外部接口
### 1.4 器件选择、库存复用、采购缺口与资料依据
### 1.5 默认状态、故障行为与固件/机械依赖

## 2. 原理图设计

### 2.1 电路分块、用途与相互关系
### 2.2 元器件用途、物理引脚与网络
### 2.3 关键计算与设计余量
### 2.4 测试点、调试/烧录接口与样机确认项
### 2.5 当前原理图实现、保存及检查状态

## 3. PCB 设计

### 3.1 板框、层叠与机械约束
### 3.2 布局功能块、成员位号与布局理由
### 3.3 网络分类、线宽/过孔、布线优先级与配色
### 3.4 关键拓扑、功率环路与回流路径
### 3.5 预留区、散热、装配与访问限制
### 3.6 当前布局、布线、铺铜、保存及 DRC 状态

## 4. 制造交接

## 5. 样机验证与改版

## 6. 产品化与正式发布

## 当前未决事项
```

没有进入的阶段不用填空表。特殊项目可调整小节，不要求编号本身充当审批状态。

顶部交接用于确定当前工作、已完成与未验证的范围、主要限制和下一个具体动作。长清单、完整检查过程及历史证据放在对应正文，顶部提供明确入口；续接所需的目标身份、输入和执行入口须能从该入口定位。“最小有用下一步”写接下来可执行的动作及必要前提，后续完整安排留在相关章节。

### 让正文真正可读

- 介绍一个设计部分时，先说明用途、当前采用的方案及关键理由，再展开必要参数、连接关系和验证依据。按主题组织说明，不强行套用同一段落模板；操作过程只保留会影响后续工作的内容，完整日志引用证据文件。
- 设计意图说明“为什么这样做”，约束注明来源和适用范围，区分硬性要求、暂定假设与待测项。
- 原理图按功能块说明工作方式，并在同文档保留器件用途表和引脚表：`位号｜器件/作用｜物理引脚号｜语义功能｜网络｜默认状态｜必连/NC/DNC`。长表按功能块分组，不只留一个 JSON 链接。
- PCB 功能块说明 `块名｜成员位号｜位置/朝向｜固定或可移动条件｜必须保持的邻接/环路｜布局理由`。块名尽量与原理图对应，记录跨块关键网络；可嵌入带来源版本的当前布局图。
- 制造部分对应同一候选的源文件、Gerber、钻孔、BOM/CPL 和检查结果；测试部分保留条件、预期、实测、结论与证据链接。

### 给 View State 的简短交接说明

可视化读取本节约定的同一份主文稿；需要打开面板时，按 [View State 启动步骤](../view-state/README.md#由-skill-拉起面板)操作。

新建或整体整理主文稿时，为顶部当前交接、已有实质内容的阶段及需要展示的设计主题编写 `ViewState:` 段落。它由 AI 理解对应内容后归纳，正文仍保留完整方案、表格和依据；日常变更只同步受影响的段落，不为尚未开展的阶段编造内容。

- 标记固定为 `ViewState:`（英文冒号），独占一个物理行，冒号后直接写一小段正文；每个章节最多一处，放在标题下、详细正文和下级标题之前，与其他内容用空行分开。不放进列表、引用、代码块或脚本生成的事实表区域。
- 用工程师给同事留说明的语气，通常一至三句话。先讲这一部分最值得知道的事，再补必要理由或限制。方案类讲采用什么、为什么；进展类讲发生什么、影响什么、接下来做什么。不写宣传式标题、通用工作介绍或操作统计，也不强行让每段都有“下一步”。
- 只概括正文和证据能够支持的内容，保留“暂定、待验证、仅检查了某范围”等关键限定；梗概中出现的新决定先落实到对应正文。长型号清单、坐标、UUID 和日志留在原文，理解结论必需的参数或位号可以保留。
- 顶部段落说明当前工作焦点，阶段段落说明整体情况，主题段落说明该部分的具体设计；不要把同一段当前状态复制到所有章节。顶部 `当前阶段:` 使用主文稿中对应的阶段标题，不含编号，不以此宣称其他阶段均已完成。
- 章节标题提供展示名称和层级，段落提供可读内容，章节位置提供原文入口。缺少标记表示未提供梗概，查看端不自行截取正文补齐，也不从梗概推断工程验收状态。旧文稿按原方式续接，不因缺少标记阻塞工作。

以下仅示意写法，内容必须根据实际项目编写：

```markdown
### 功率区布局

ViewState: 更换电感后，原位置与周围器件的间距不足，需要调整局部布局。右侧显示接口保持不动，补线后还要重新检查。

这里继续说明实际布局、必须保持的关系、调整理由和检查依据。
```

## 信息归属与更新

| 事实 | 来源 | 主文稿中的视图 |
| --- | --- | --- |
| 需求、限制、选择理由 | 用户决定与当前设计依据 | 正文解释和已接受决定 |
| 器件及引脚网络意图 | Contract；物理引脚号核对准确资料与 Provider 映射 | 可读器件/引脚表，注明来源版本 |
| 实际器件、连接与布局 | EDA 源文件及回读 | 已实现范围、布局关系、图与检查结论 |
| 制造与样机表现 | 制造输出、原始测量和测试记录 | 候选、条件、结果与限制 |

先更新拥有事实的制品，再刷新正文对应视图。可读表格可以完整，但不能与 Contract/EDA 各自独立手填。缺少引脚号、映射或回读时明确标未知，不将设计意图冒充实际实现。

普通正文与结构化记录都须区分计划、写入、保存、DRC、连通、电气和样机验证。检查结论注明对应对象或版本、检查范围、检查发生时间及证据入口，可由同一段落或表格集中说明；会话连接等临时观察不能写成长期有效的当前状态。设计变更后核对受影响结论是否仍适用；文稿更新时间不代表重新检查时间，无法确认的结果标为待核对。

稳定设计变更、阶段切换或交接时，按变更的位号、旧料号、网络、接口或功能定位相关正文和表格。AI 更新设计理由、取舍和历史说明，脚本刷新可计算的事实。新结论形成后，修改对应位置的当前说明；有保留价值的旧方案或旧检查结果标为历史，注明所属版本或时间及被替代原因，保留必要证据链接。不只在顶部追加新状态而让失效表述继续作为当前结论；依据冲突且尚未核实时，明确冲突和待核对内容，不仅按段落位置或文件时间选择结论。

更新结束前，核对本次变更涉及的顶部交接（含当前阶段）、正文、事实表、未决事项和 `ViewState:` 段落是否一致。已解决事项移出当前未决，仍有价值的结果归入对应正文；未同步部分明确标注，不因现场检查通过就宣称交接完成。只检查受影响范围，不重写无关章节；无变化不重写，小批次不重复生成整份文稿或重跑 EDA 检查。

主文稿保存当前设计和仍有价值的选择理由，不追加聊天流水账。需要多轮实验的活动问题按 [0.2 调试](0.2-debug-loop.md) 使用临时记录，稳定结论仍回到此文档。

## 按需生成原理图事实表

重复维护器件、引脚网络、NC 和延期项时，可用独立的 [handoff-sync.mjs](../scripts/handoff-sync.mjs)。它仅消费已有 Contract v1、可选 Snapshot v1（或成功的 `schematic-inspect` 报告），不连接 EDA、不调用连线规划器、不更新其他项目状态。简单项目仍可直接维护正文，不强制采用。

```text
node <skill>/scripts/handoff-sync.mjs --project-root <项目> --contract design/contract.json [--snapshot evidence/inspect.json] [--connections design/connections.json]
```

路径相对于项目根目录，须为项目内文件。`--connections` 只读取已有连接配置的预期目标、`deferredComponents` 和 `providerPinNoConnect`，不读取布局或连线策略。默认输出简短预览摘要；`--print` 才输出完整拟生成区。`--check` 比较当前生成区与输入是否一致，返回非零表示缺失、变化或人工编辑，不等于电路检查失败。

仅在本次确实需要更新文稿时使用 `--apply`。它只更新已有 `CURRENT_HANDOFF.md` 中唯一的一组独立行标记之间的内容：

```html
<!-- flitrealize:facts:start -->
<!-- flitrealize:facts:end -->
```

初次采用时明确选择插入位置，放入空标记；脚本不自动创建文稿或追加区域。内容相同不写文件、不刷新时间；默认预览与检查不产生报告、缓存或状态文件。写入只替换生成区，并保留区域外文字；生成区被人工编辑时拒绝覆盖，先查看差异再处理。

表格分列设计意图和快照观察，并记录输入文件指纹、目标与快照原始时间。缺少映射、型号、封装或实际网络就显示未提供/未核验，不猜测；快照没有报告网络不等于引脚未连接。它不解析任意 DRC/保存报告、不推断库存采购、不验证工程语义。复用本批次回读；跨会话、用户手改或需确认当前现场时再按 Provider 规则重新回读。普通续接按功能块读取相关表格，不把完整表格每次送入上下文。

## 证据与结构化续接

长流程可在同一文稿顶部使用一个 `flitrealize-handoff` 结构块，记录当前入口、输入版本、检查范围和证据。它替代同义的机器交接字段，不另建项目状态库，也不取代可读设计正文；目标、限制和下一步用中文，技术字段可放在折叠区。

已有结构块时运行：

```text
node <skill>/scripts/handoff-check.mjs inspect --project-root <项目绝对路径>
```

它只检查本地引用：退出码 0 为结构和指纹一致，1 为引用缺失或变化，2 为旧格式/缺少交接/输入无效。没有结构块仍按正文续接，不因格式阻塞项目。首次建立或修改格式时才读 [0.5 记录格式](0.5-handoff-record.md)。

记录以实际范围为准：`planned` 是方案，`applied` 是写入，`verified` 是特定检查通过，`blocked` 是缺少条件，`unknown` 是无法确认结果。保存、DRC、连通、电气和样机功能是不同检查；文件存在或指纹相同不证明这些检查通过。

引用变化时核对受影响事实，不把全部阶段清零，也不只刷新哈希消除告警。用户手改、重开文档或未知写入后，按 [0.3 Provider 恢复规则](0.3-easyeda-pro.md) 回读现场，再更新相关章节与下一步。
