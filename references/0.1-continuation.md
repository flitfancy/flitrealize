# 0.1 Continue an existing project

Read this reference when resuming an existing project or handing current progress to a later task.

The goal is to recover only the state that remains valid, then continue the user's current work.

## Recover current state

1. Confirm the project root.
2. Read `CURRENT_HANDOFF.md` at that root.
3. Use its current goal, major decisions, and next step to load only the design files needed by this task.
4. Check that the listed files still exist and belong to the current project version.
5. Continue directly when the new request is compatible. Ask only when the write target is unclear or an important accepted change would be overwritten.

Different sources own different facts:

- The user's current request owns this task's goal, scope, and authorization.
- `CURRENT_HANDOFF.md` explains the project's current decisions and entrypoints.
- Current design files, EDA source, and live reads show what is implemented.
- `DEBUG_NOTES.md` covers only one local issue still under repeated experiment.

When they conflict, inspect the current artifact that owns the fact. Do not infer state from sibling projects, old conversations, filenames, or memory.

## What CURRENT_HANDOFF.md stores

Keep one `CURRENT_HANDOFF.md` at the project root. It should tell the next task:

- what the project is;
- its current goal and scope;
- the major accepted decisions;
- the active design, EDA, and validation files;
- unresolved questions or assumptions;
- the single most useful next step.

It stores current state, not full history. Leave rejected options, discussion, and obsolete conclusions to version history or a separate record.

Use a compact shape:

```markdown
# <Project name>

Updated: <time>
Project root: <path>

## Current goal
## Accepted decisions
## Current files
## Open questions
## Next step
```

Write only established facts. Mark provisional values, assumptions, and test items clearly.

## When to update it

Update after a stable change that matters to later work, such as:

- a changed goal or stage;
- an accepted architecture, part, or interface;
- a new authoritative schematic, PCB, or manufacturing candidate;
- a resolved important issue;
- a physical measurement that confirms or overturns a decision;
- a changed next step.

Routine reads, one-off commands, temporary output, and work that does not change the project decision do not belong in the handoff.

Edit the handoff into the new current state. Remove obsolete conclusions instead of appending a chat-like timeline.

## Relationship to debugging notes

Read `DEBUG_NOTES.md` after the handoff only when one local issue needs repeated experiments. It cannot change project identity, overall scope, or unrelated stable design decisions.

When the issue stabilizes, merge the necessary conclusion and evidence pointer into the handoff, then archive or delete the debugging note. See [0.2-debug-loop.md](0.2-debug-loop.md).

## Finish continuation

After recovery, be able to state:

- which project is being changed;
- which files are current entrypoints;
- which conclusions are accepted;
- which questions remain open;
- what this task will complete;
- how success will be recognized.

Once that is clear, stop reading history and enter the current stage.
