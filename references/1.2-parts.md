# 1.2 Part selection and source material

Read this reference when the design must select parts, match existing inventory, or obtain datasheets.

Part selection serves the circuit first and does not depend on a specific EDA library.

## Workflow

```text
AI defines the part role and important requirements
    ↓
Read available inventory
    ↓
Propose an exact part or a small candidate set
    ↓
Resolver checks the local source library and retrieves missing material
    ↓
AI reads only the facts needed by the current decision
    ↓
Accept a part or keep a candidate set
    ↓
Enter the schematic Contract
    ↓
Bind the EDA identity last
```

AI owns circuit judgment and final selection.

Scripts own repeated deterministic work such as:

- local source lookup;
- retrieval from an exact product identity;
- PDF download and file checks;
- recording source, file identity, and local path;
- combining inventory and source status.

A script must not decide circuit suitability from a storefront category, parameter summary, or ranking alone.

## Start from circuit requirements

Before selecting a part, state its role and the conditions that actually affect the choice, such as:

- voltage, current, power, and frequency range;
- accuracy, efficiency, noise, temperature rise, or timing;
- package, size, and cooling;
- required protection or control behavior;
- supply, stock, and cost constraints.

Do not fill a universal template with parameters irrelevant to this part.

Check available inventory first. Prefer an in-stock part only when its identity is reliable, its parameters fit, and its package is usable. Do not force unsuitable stock into the design.

When inventory has no suitable item, retain a small candidate set and create a purchase list.

## Part identity

Record identity at the precision the design actually needs:

- **exact:** manufacturer, exact MPN, suffix, and package are confirmed;
- **generic:** value, required ratings, tolerance, package, and allowed range define the part without locking one MPN;
- **unresolved:** available evidence is insufficient or no part meets the hard requirements yet.

Protection, power conversion, battery management, critical interfaces, and other parts that directly determine core function should be `exact` before the full schematic implementation, including pinout, package, and critical ratings.

Ordinary resistors and capacitors may remain `generic`. Connectors, switches, and other mechanical parts should be `exact` before the implementation stage in which their pins or PCB geometry matter.

Keep parts still under comparison in the selection record. Only an accepted identity enters the current Contract.

## Use the local source library

When a shared part-source library is configured, the resolver checks it first.

```text
parts-database/
├── C470965/
│   ├── part.json
│   └── datasheet.pdf
└── MPN_TPS25221DBVR/
    ├── part.json
    └── datasheet.pdf
```

An exact local match returns without a network request.

When material is missing, the resolver may retrieve exact product information and a datasheet from a supported source, then cache the result for later projects.

The shared library is tool data, not the authority for one project's design. The project still records the manufacturer, MPN or generic specification, package, and selection reason it actually uses.

## Sources

Large official marketplaces, authorized distributors, and manufacturer sites can directly establish:

- manufacturer;
- exact MPN;
- purchasing code;
- package;
- stock and price;
- datasheet URL.

When these identities do not conflict, do not search several sources merely to prove the same basic facts again.

Use the manufacturer datasheet for electrical design facts. Enter CURIOUS_MODE only for the affected part when:

- storefront identity conflicts with manufacturer material;
- the exact suffix or package is unclear;
- the design depends on curves, temperature rise, transients, derating, or mechanical timing;
- the datasheet does not answer a core design question directly;
- the part provides protection, isolation, or fault shutdown.

Return to DEFAULT_MODE once the question is resolved or converted into a precise prototype test.

## Use the resolver

Provide known exact identity and necessary keywords when possible:

```json
{
  "lcsc": "C536262",
  "manufacturer": "Infineon",
  "mpn": "IM69D130V01",
  "keywords": ["PDM", "4x3mm"]
}
```

Use the script's current `--help` for exact options. The base entrypoint is:

```text
node <skill>/scripts/parts/parts-resolver.mjs \
  --project-root <project> \
  --database-root <parts-database> \
  --input <project-relative-input>
```

Each item returns one retrieval result:

- `local`: exact material already exists locally;
- `downloaded`: exact material was retrieved and cached;
- `needs_lookup`: AI should perform one focused lookup using the returned identity and keywords;
- `error`: exact material was not obtained.

These states describe source retrieval, not circuit approval.

If a source code has become invalid, AI may make one focused search using the exact manufacturer, MPN, and keywords, then return the confirmed datasheet URL to the resolver for storage.

If exact identity still cannot be confirmed, keep it unresolved. Do not substitute a similar name or the first search result automatically.

The resolver is an exact-source retrieval tool, not a general web crawler.

## Read datasheets selectively

Downloading is not review.

In DEFAULT_MODE, read only what the selection needs, such as:

- ratings and recommended operating conditions;
- pinout and package;
- critical electrical parameters;
- typical application and external components;
- protection, startup, or fault behavior used by this circuit.

Do not open every cached PDF automatically.

CURIOUS_MODE reads deeper only for the exact affected part and relevant section. A category name alone does not trigger a full source audit.

## Inventory and source summary

The source inventory continues to record what the user actually owns.

The part-source library records retrieved identities and datasheets.

An AI-readable inventory CSV may combine them into a read-only view with fields such as:

- whether local material exists;
- local source directory;
- current exact MPN;
- latest source.

The generator derives these fields from the current source library. The user does not maintain them manually in the inventory workbook.

After new material is retrieved, the current task can use the returned path immediately. Regenerate the inventory CSV later when subsequent tasks need the updated combined view.

The resolver does not edit the user's inventory workbook.

## Save selection results

For each accepted part, record at least:

- circuit role;
- manufacturer and exact MPN for an `exact` part, or complete specification for a `generic` part;
- package;
- purchasing identity used by this project;
- parameters that drove selection;
- datasheet or local source path;
- conditions still requiring prototype confirmation.

When a part enters the schematic, write the accepted identity and required parameters into [2.1-schematic-contract.md](2.1-schematic-contract.md).

This stage also owns the allowed substitution range and its conditions. Manufacturing preparation chooses the actual order item only from accepted parts or substitutions. Productization owns long-term supply and production substitution policy.
