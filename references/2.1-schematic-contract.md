# 2.1 原理图设计与 Contract

建立或修改电路意图、Contract 或需要传递PCB电气要求时读取。已确认设计的单项EDA操作直接使用对应操作说明，不重新加载上游所有阶段。

## 上游提供什么

| 来源 | 本阶段需要的内容 |
| --- | --- |
| [需求与架构](1.1-requirements-and-architecture.md) | 功能块、输入输出、电源树、工作条件、接口和机械限制 |
| [器件选择](1.2-parts.md) | 器件身份、规格、封装、资料来源及未决项 |
| 数据手册与设计计算 | 引脚功能、额定条件、推荐连接、参数计算和依据 |
| 已有 Contract 与 EDA 回读 | 当前设计意图、实际连接及两者差异 |

需要重新选择架构或器件时，更新对应的上游决定；已经明确的部分可以继续设计。

## Contract 保存什么

项目原理图意图保存在 `design/SCHEMATIC_CONTRACT.v1.json`，格式见 [SchematicContract Schema](../schemas/schematic-contract.v1.schema.json)。画布坐标和显示样式由 EDA 保存；设计理由、计算过程与取舍保留在项目主文稿。

### 顶层结构

以下字段需要存在。数组中明确没有对应项目时使用 `[]`；尚未确定的内容记录未决状态。

| 字段 | 内容 |
| --- | --- |
| `kind`、`schemaVersion` | 固定为 `flitrealize.schematic-contract` 和 `1` |
| `project` | 项目标识 `id`、修订号 `revision`；可附标题和来源制品 |
| `blocks` | 功能块的 `id`、`purpose`、成员位号 `components` |
| `powerDomains` | 电源域的 `id`、供电网络 `sourceNet`、返回网络 `returnNet`，以及已知电压范围 |
| `interfaces` | 接口 `id` 和 `signals`；信号包含 `name`、`net`、`direction`，可附电压域和默认状态 |
| `components` | 器件身份、封装、引脚、用途和 BOM／PCB 范围 |
| `nets` | 网络的 `name`、`kind` 和端点 `endpoints` |
| `constraints` | 对具体对象的设计要求、依据和确认状态 |
| `exceptions` | 有意例外及其理由、适用对象和确认状态 |

### 器件

每个 `components[]` 条目包含：

| 字段 | 填写方式 |
| --- | --- |
| `designator`、`role` | 唯一位号及器件在本电路中的作用 |
| `identity` | `selection` 为 `exact`、`generic` 或 `unresolved`。准确器件填写 `mpn` 及已确认的制造商信息；通用器件填写 `value` 或 `description` |
| `footprint` | `selection` 为 `exact` 时填写 `name`，为 `policy` 时填写 `policy`；未确定为 `unresolved` |
| `pinMapCoverage` | 声明引脚范围：`critical` 为关键引脚，`complete` 为完整逻辑引脚 |
| `pins` | 本项目声明的引脚条目 |
| `includeInBom`、`includeInPcb` | 明确是否纳入 BOM 和 PCB |

数值放在 `identity.value`；额定值、公差和选用条件可写入 `identity.description`。需要独立检查的限制放在 `constraints`，关联对应器件。程序需要读取的附加结构使用约定的 `extensions`。

`pinMapCoverage` 是设计声明，实际引脚及封装焊盘仍通过数据手册和 Provider 映射核对。

### 引脚与网络

单个引脚条目示例：

```json
{
  "number": "1",
  "function": "VIN",
  "classification": "power-in"
}
```

- `number` 是本器件内唯一的引脚标识，网络端点通过它引用引脚。它可以采用已确认的编号，也可以采用明确的逻辑标识。
- `function` 描述该引脚的功能；多个引脚可以有相同功能，仍保留各自标识。
- `classification` 描述类别，可选值见 Schema。`no-connect` 和 `dnc` 引脚不分配网络。
- `safeDefault` 可记录上电、复位或失控时要求的状态。

网络端点使用 `{component, pin}`。例如 `{"component": "U1", "pin": "1"}` 引用 U1 的 `pins[].number: "1"`；同一引脚只属于一个网络。

Provider 的 `bindings` 保存库身份及 Contract 引脚与原生引脚的映射。具体操作见 [器件绑定与放置](providers/easyeda-pro/2.3-component-batch.md)。引脚功能来自准确器件资料，实际画出的连接由 EDA 回读确认。

### 要求、例外与依据

`constraints[]` 使用 `id`、`type`、`appliesTo`、`requirement`、`evidenceState`。要求中的数值注明单位和适用条件，来源可放在 `evidenceRefs`。

`appliesTo` 指向已声明对象，例如：

```json
{"kind": "component", "id": "U1"}
```

`exceptions[]` 使用 `id`、`rule`、`appliesTo`、`rationale`、`evidenceState`，说明有意例外及其依据。

`evidenceState` 为 `OPEN`、`CONDITIONAL` 或 `PASSED`，分别表示未决、有条件成立、已有依据确认。确认状态针对所记录的要求，不代表整个电路通过验收。

## 引脚调整

需要调整引脚时，核对候选引脚的功能复用、电气能力、上电默认状态、调试用途及固件依赖，并遵守项目已有的固定要求。

确定调整后，同步 Contract 端点、Provider 映射、实际原理图和受影响的固件接口；在主文稿记录调整理由。

## 向 PCB 传递什么

| 电气意图 | 保存位置 |
| --- | --- |
| 功能块归属、接口、电源域及连接拓扑 | `blocks`、`interfaces`、`powerDomains`、`nets` |
| 电流、电压、压降、时序、回流、保护等要求 | 对应对象的 `constraints`，计算与依据放主文稿 |
| 去耦、采样、功率路径中需要影响布局的端点关系 | `extensions.pcbLayout` |
| 已确认的线宽、过孔、阻抗或长度要求 | 对应网络的约束及其计算条件 |

电气关系说明服务对象、相关引脚、网络和依据；字段见 [PCB 布局输入](pcb-layout-inputs.md)。器件用途本身不提供距离数值，有依据的上限另行填写。

布局阶段新确认的电气关系补回 Contract。接口侧别、安装空间和装配间距放在项目 PCB 配置；位置和焊盘几何由当前 PCB 回读取得。

## 检查与交接

运行结构检查：

```text
node <skill>/scripts/action-runner.mjs run \
  --action schematic-contract-audit \
  --input-file <schematic-contract.json>
```

检查器核对字段、身份、引用、引脚网络归属、NC／DNC、电源域及接口关系。电路拓扑、额定值、默认状态和保护行为仍按资料与设计计算核验。

报告中的 `passed` 和 `conditional` 均可表示结构检查可继续；`conditional` 保留未决身份或依据。下一步能否执行，取决于本次范围所需的器件、映射和几何是否具备。

按本次要实现的范围确认器件、封装、引脚和连接。缺项、未决问题及其影响明确记录；探索性布局标明采用的输入范围与假设，自动求解和实际写入按对应入口的输入要求执行。

进入 EDA 使用 [原理图操作说明](providers/easyeda-pro/2.2-schematic-workflow.md)。写入后对照 Contract 与实际器件、引脚、网络和属性，差异回到拥有错误事实的一侧修正。

交给 PCB 的内容包括当前 Contract、对应原理图及保存状态、连接核对结果、相关电气要求和剩余未决项。主文稿保留电路工作方式、关键计算、可读器件／引脚表与检查结论，更新方法见 [项目主文稿](0.1-continuation.md)。
