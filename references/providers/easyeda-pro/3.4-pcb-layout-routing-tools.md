# 3.4 PCB 布局、线宽、优先级与配色入口

需要比较功能块布局、检查空白区域、调整指定线段宽度、整理布线顺序或设置 PCB 网络颜色时读取。设计依据仍见 [3.1](../../3.1-pcb-review.md)，不是用几何脚本代替电气判断。

这些入口由项目内的放置、功能块平移、空白网格检查、线宽和配色脚本提炼而来；未继承任何项目 UUID、位号、板框、电流或线宽值。配色采用下文固定用途/信号色表，旧项目脚本保留。通用版已通过隔离模拟和打包测试，首次接入真实 EDA 仍须验证代表对象，不把历史项目成功等同于新入口已验收。

## 先发现，再选择实际操作

```text
node <skill>/scripts/action-runner.mjs list --domain pcb --query "布局优化"
node <skill>/scripts/action-runner.mjs list --domain pcb --query "线宽"
node <skill>/scripts/action-runner.mjs list --domain pcb --query "走线优先级"
node <skill>/scripts/action-runner.mjs list --domain pcb --query "配色"
node <skill>/scripts/action-runner.mjs list --domain pcb --query "板框"
```

矩形板框创建见 [3.2](3.2-pcb-foundation.md) 的 `pcb-board-outline`（layer 11 Polyline），不走本页的 `pcb-edit` 封装。

| Action | 输入 | 实际产出 |
| --- | --- | --- |
| `pcb-placement` | 目标、矩形边界、固定器件、预留区、明确移动/候选 | 包围盒冲突、最大器件空白矩形、候选计划、指定移动与回读 |
| `pcb-routing-plan` | 已确定的网络分类/宽度/优先级；可选线段角色 | 离线有序布线计划、指定线段改宽请求、可选配色请求 |
| `pcb-trace-width` | 目标、网络、明确线段 ID、目标线宽 | 只修改指定线段宽度，保留其他线段，配置 DRC 和回读 |
| `pcb-net-color` | 目标、已有网络类的完整成员及 kind 或颜色 | 重建选定网络类并回读不透明颜色，保留成员和规则 |

`pcb-routing-plan` 只有 `generate`；`pcb-net-color` 使用 `inspect / plan / apply`，apply 内部完成回读和可选保存。布局与线宽仍使用 `inspect → plan → apply → verify → save`，apply 与 save 是独立写入。

## 共用调用和证据

所有 EDA 请求必须给出现场确认的 `expectedProjectUuid`、`expectedDocumentUuid`。参数坐标、线宽单位均为 mil，不自动猜测 mm。不要从另一块板复制值。

```text
node <skill>/scripts/pcb-edit.mjs --action pcb-placement --project-root <当前项目> --window-id <窗口> --input-file <plan-input.json>
node <skill>/scripts/pcb-edit.mjs --action pcb-placement --project-root <当前项目> --window-id <窗口> --input-file <plan-input.json> --candidate <唯一候选名> --apply
node <skill>/scripts/pcb-edit.mjs --project-root <当前项目> --window-id <窗口> --resume-save <本项目成功apply报告或result.json> --apply
```

统一入口是 [pcb-edit.mjs](../../../scripts/pcb-edit.mjs)，`--action` 也可选 `pcb-trace-width` 或 `pcb-net-color`。直接使用本页已有 Action 的 plan 输入，不新增一套参数格式；普通单方案不填 `--candidate`。默认只读 EDA 并把计划、输入和报告写入本项目 `evidence/pcb-edit/<唯一运行目录>/`，不是纯本地无副作用查询。

1. 检查计划范围、候选 issues 和报告中的源码备份。多候选写入必须明确给唯一候选名；冲突方案不能执行。
2. `--apply` 对布局与线宽衔接 plan → apply → verify → save → 保存后 verify；配色只调用 plan → apply，apply 内完成回读与保存。逐步保留输入与报告，任何失败即停。
3. 布局与线宽保存得到确定失败结果时使用 `--resume-save`：验证项目内成功 apply 报告的项目归属、目标、请求及当前指纹，再 verify → save → verify，绝不重放 apply。现场已变化或保存仍未知/在执行时先对账，不强行续存。
4. `result.json` 汇总本次结果并引用分步证据。只读 verify 的成功不是整板验收；将实际检查范围和稳定结论同步到同一份 `CURRENT_HANDOFF.md`。

配色不使用 `--resume-save`。以下指纹、单独 verify/save 与保存占用记录说明适用于布局和线宽；配色流程见本页末节。

需要 inspect 或单独一步时仍可使用 `action-runner.mjs run --action <name>`，沿返回的 `applyRequest`、`verifyRequest`、`saveRequest` 传递；写入加 `--allow-write`。不必在普通完整流程中手工拆装这些 JSON。

只读 verify 不查询编辑器的保存状态，返回 `saved: null, saveChecked: false`。这既不证明未保存，也不覆盖之前独立 save 报告的结果；结合 save 报告和保存后的现场指纹判断。

返回的 applyRequest 绑定当前源码和已读对象指纹。用户修改、换板或输入目标错误会被拒绝。调用期间不要有第二个写入者；这些 Action 不提供跨进程事务锁，也不具备原理图批量入口的自动续接机制。

薄封装会为同一成功 apply 的保存尝试保留本地占用记录（`evidence/pcb-edit/save-attempts/`），避免通过 result、原 apply 报告或其副本重复发起未决保存。确定终态后释放，未知或进程中断时保留；不要靠删记录绕过，先确认旧执行结束并核对现场。它只保护这条保存链，不证明其他 EDA 写入者不存在，也不是新的项目交接文档。

若写入失败，报告返回 `apply-failed`、写入前快照、已尝试 ID/网络以及能取得的当前回读，不自动回滚或保存。超时且没有确定终态时先确认旧执行已停止，核对现场后再计划受影响增量；不能假设“没收到成功就没写入”。源码备份不应整图导入覆盖后续用户修改。

## 布局和空白检查

先固定机械接口与关键功率/敏感功能块，再把允许移动的小块作为候选移向空白区。布局脚本不替你决定电源环路、电气隔离或哪个块重要。

示例只展示字段，不是任何实际电路的推荐尺寸：

```json
{
  "mode": "plan",
  "expectedProjectUuid": "<实际项目 UUID>",
  "expectedDocumentUuid": "<实际 PCB UUID>",
  "boardBounds": {"minX": 0, "minY": 0, "maxX": 2000, "maxY": 1200},
  "lockedDesignators": ["J1", "U1", "L1"],
  "reservedRegions": [{"name": "display", "bbox": {"minX": 1400, "minY": 800, "maxX": 1900, "maxY": 1100}}],
  "clearanceMil": 5,
  "cellMil": 50,
  "scenarios": [
    {"name": "move-control-left", "groups": [{"designators": ["U3", "C8", "R9"], "dxMil": -100, "dyMil": 0}]},
    {"name": "move-control-down", "groups": [{"designators": ["U3", "C8", "R9"], "dxMil": 0, "dyMil": 100}]}
  ]
}
```

- 单方案不用 `scenarios`，直接给 `groups` 或 `placements: [{designator, x, y, rotation?}]`。未给 rotation 时保留当前旋转，不默认归零；组内只平移，保持相对关系。旋转仅支持相对当前角度的 90° 整数倍。
- `lockedDesignators` 和 `reservedRegions` 必须显式给出，确认没有约束时才用空数组。EDA 自身已锁定器件也不能移动；先核对锁定对象，不通过脚本解除锁。
- 现场所有 Region 的包围盒也作为保守障碍，可能比实际禁布范围大。尚未体现在 Region 中的屏幕、装配、天线、散热预留必须通过输入提供。
- `inspect` 只给目标即可读取完整器件快照；需要空白分析时再给上述边界/约束，不需给移动项。
- 最大空白矩形仅基于网格中的器件/Region 包围盒，不代表可压缩面积或可用布线面积；网格越粗越保守。对侧器件也保守计入，不自动假设可重叠。
- 仅支持明确矩形边界，不处理异形轮廓、孔槽或复杂三维干涉；这些条件不满足时改用真实几何检查，不伪造矩形验收。
- 每批最多 100 个器件、最多 20 个候选、网格最多 100000 格。先比较少量有依据的候选，不枚举任意坐标。
- **存在铜层线路、圆弧、折线、过孔或铺铜时，不执行器件移动**，因为本入口不会带动导线或自动清线。已布线板先按用户意图单独处理受影响走线，或使用适合已布线调整的工具。当前源备份不能替代这项约束。

plan 返回每个候选的 `issues`、`changedCount`、`space` 和可用的 applyRequest。apply 回读目标及未移动器件的已读属性；包围盒无冲突不等于焊盘间距、连通性、热设计或整板 DRC 合格。

## 网络规则与优先级

`pcb-routing-plan` 是本地 Action，不需要 Bridge：

```json
{
  "mode": "generate",
  "requireColor": true,
  "netNames": ["PWR", "GND", "CTRL"],
  "expectedProjectUuid": "<实际项目 UUID>",
  "expectedDocumentUuid": "<实际 PCB UUID>",
  "rules": {
    "units": "mil",
    "generalClearanceMil": 6,
    "qfnEscape": {"widthMil": 6, "maxLengthMil": 60},
    "classes": [
      {"name": "power", "priority": 1, "nets": ["PWR"], "trunkWidthMil": 25, "localWidthMil": 12, "viaHoleMil": 12, "viaDiameterMil": 24, "kind": "power"},
      {"name": "ground", "priority": 1, "nets": ["GND"], "widthMil": 20, "kind": "ground"},
      {"name": "control", "priority": 2, "nets": ["CTRL"], "widthMil": 8, "kind": "logic"}
    ],
    "routingOrder": ["power", "ground", "control"]
  },
  "segmentAssignments": [{"net": "PWR", "role": "trunk", "primitiveIds": ["<实际线段 ID>"]}]
}
```

数字只是格式样例。实际宽度、过孔、间距须按当前电流、压降、铜厚、温升及制造条件确定。每条网络只能属于一个类；priority 越小越先，同级保持输入顺序。可选 routingOrder 必须与排序一致，避免两套优先级冲突。可选 `selectNets` 只选择本次网络范围。

输出 `sequence` 中每组状态都是 planned，不相信输入里的 completed/进度字段。后续执行者按序完成关键组，回读拓扑、线宽、连接和 DRC，再继续普通网络；交接中留相应证据。**有序计划不等于自动布线器执行顺序已设置**。

`pcb-routing-plan` contractVersion=3：配色任务设置 `requireColor: true`，必须提供实际项目/PCB UUID、完整 `netNames`，并为每个选中类提供 kind 或 color。全部缺少配色信息也报 `COLOR_KIND_REQUIRED`，不退回纯布线。requireColor 只接受布尔值，netNames 必须为非空、无重复且名称无首尾空白的字符串数组；对应错误为 `INVALID_COLOR_REQUIREMENT` 和 `INVALID_NET_INVENTORY`。

netNames 来自目标 PCB 的实际网络清单，不从 rules.classes 派生。提供 netNames 时：未传 selectNets 则检查分类覆盖全部网络，包括 GND；传了 selectNets 则只要求本次网络有分类，不要求未选网络都参与上色。输入类中的网络都必须存在于 netNames；遗漏或未知网络报 `NET_COVERAGE_MISMATCH` 并列出名称。selectNets 仍须为唯一、已分类的网络，且配色只能选择完整类。此检查证明与所提供清单一致，清单的目标归属和时效由上游确认。

省略 requireColor 或设为 false 时沿用旧行为：选中类全无配色信息则仅生成布线计划；只要有一个提供 kind/color，就要求全部选中类都提供。false 不表示禁用已有配色。纯离线布线仍可省略目标 UUID 和 netNames。脚本不猜用途；具体 kind 是否有效由着色核心检查。

通过命令取得配色输入：

```text
node <skill>/scripts/action-runner.mjs run --action pcb-routing-plan --project-root <项目> --input-file <布线配置.json> --report-file <项目内规划报告.json> --full
```

先确认命令成功，再取标准输出中的 `result.colorPlanRequest`；读取报告时取 `response.result.colorPlanRequest`。将该对象单独保存为项目配色输入，不能把整份输出或报告交给 pcb-edit。默认摘要不包含请求正文。然后调用：

```text
node <skill>/scripts/pcb-edit.mjs --project-root <项目> --action pcb-net-color --window-id <窗口> --input-file <配色输入.json> --apply
```

已有 PCB 规则配置作为源时，配色输入为派生产物；分类变化后重新生成，不独立编辑第二套成员。上述例子只展示结构，包含 GND 不代表规划器会生成铺铜。

对已经存在的走线，先用 `pcb-trace-width inspect` 获取真实 ID，再按用途给 `segmentAssignments`：`trunk`、`local`、`signal` 或 `escape`。分别选对应 class 宽度或 qfnEscape 宽度；不从线段长度猜测角色。提供目标 UUID 后，输出 `widthPlanRequest` 可交给 `pcb-trace-width`；class 给出 kind 或 color 时输出带类名及完整成员的 `colorPlanRequest`，直接交给 `pcb-net-color`。上游只传递用途和已有分类，配色核心维护固定用途/信号色表；同 kind 跨项目保持同色，显式 color 优先。执行前须确认网络类已存在且成员完全匹配。`selectNets` 只选择某类部分网络时，不能为该类同时生成配色请求；仅生成局部布线计划时，在本次请求的所有选中类中省略 kind 和 color，保留源配置中的用途信息。生成请求不是写入。

本入口不写 EDA 网络类、不创建线路、不调用自动路由器。via、差分间距、逃逸最大长度和敏感性约束保留为设计与后续检查要求；改线宽脚本不会自动执行这些约束。

## 指定线段改宽

```json
{
  "mode": "plan",
  "expectedProjectUuid": "<实际项目 UUID>",
  "expectedDocumentUuid": "<实际 PCB UUID>",
  "rules": [{"net": "PWR", "primitiveIds": ["<主干线段 ID>"], "targetWidthMil": 25}]
}
```

inspect 返回 `state.lines` 中的 ID、网络、层、端点、线宽和锁定状态。必须显式选择 ID，最多 200 段，不接受“全部同网统一加粗”的隐式范围。拒绝重复 ID、网络不符、非铜层对象和锁定线段。可加宽或减窄，因此每次目标值必须有设计依据。

plan 记录当前配置 DRC 的详细问题基线，允许带已有问题制定修复计划。apply 前基线必须仍一致；修改后和保存前允许原问题保留或消失，但拒绝新增或变化的问题。比较完整记录的多重集合，不只比较数量；未知返回仍停止。仍有旧问题时 `drc.passed: false` 如实保留，改宽/保存成功不等于 DRC 全通过。

apply 也检查未选中直线属性。旧请求缺少 `drcBaseline` 时需重新计划；DRC 返回结构或文字变化可能保守地触发对账，不自动忽略。局部读回与 DRC 差异检查不代表全网最窄截面、焊盘、过孔和载流能力已合格。

## PCB 网络配色

项目提供已有网络类的名称和用途，着色模块只查固定色表并执行。分类属于上一层；本脚本不推断电气用途、不新增或拆分网络类、不改变成员。一个类包含多个网络时仍只有一种颜色，需要分别着色就由上游先完成分类。同 kind 跨项目、调用顺序和批次保持同色，不设置推荐色、候补色或自动轮换。

```json
{
  "mode": "plan",
  "expectedProjectUuid": "<实际项目 UUID>",
  "expectedDocumentUuid": "<实际 PCB UUID>",
  "rules": [
    {"name": "POWER", "nets": ["PWR"], "kind": "power"},
    {"name": "GND", "nets": ["GND"], "kind": "ground"},
    {"name": "CONTROL", "nets": ["CTRL"], "kind": "logic"},
    {"name": "I2C_CLOCK", "nets": ["SCL"], "kind": "i2c_scl"},
    {"name": "I2C_DATA", "nets": ["SDA"], "kind": "i2c_sda"}
  ]
}
```

以上成员仅为格式示例，须换成实际完整成员。持久化的上游配色输入保留 nets，以便在计划阶段发现成员变化；API 仍支持临时按类名查询并着色。

调用现有 `pcb-edit.mjs --action pcb-net-color --project-root <项目> --window-id <窗口> --input-file <输入.json>` 预览；加 `--apply` 后执行并保存。预览会把当前成员和确定的色值放入 applyRequest，执行时再次核对成员。

直接通过 action-runner 调用时：`inspect` 读取网络类和色表；`plan` 只预览；`apply` 一次完成改色、恢复受影响规则和回读，只有 `save: true` 才保存。写入仍需 `--allow-write`。配色不再单独调用 verify/save，也不使用 --resume-save；旧的 fingerprint/plan 包装请求需重新生成。

上下游统一使用 `rules: [{name, nets?, kind?, color?}]`。上游布线计划的 `colorPlanRequest` 可直接作为命令入口输入，不需要重新拼装；只传完整 nets 的旧输入仍可唯一匹配已有类。kind 若提供须为非空且无首尾空格的字符串，color 若提供须为六位 HEX；null 不表示恢复默认。有效 color 优先于 kind，具体 kind 色表只在配色核心维护。

类名不得带首尾空格。上游纯离线布线可省略目标；一旦提供项目/PCB UUID，就必须两个都完整提供。requireColor=true 时必须提供两个 UUID，确保返回可执行的配色请求。

当前接口约定（Action contractVersion=4）：

| 调用 | 主要返回字段 |
| --- | --- |
| `inspect` | `status: inspected`、`target`、`classes`、`palette` |
| `plan` | `status: planned`、`assignments`、`changedCount`、可直接执行的 `applyRequest` |
| `apply` 成功 | `status: applied`、`assignments`、`changedCount`、`saved` |
| 写入中失败 | `status: apply-failed`、`error`、`before`、`attempted`、`saved` |
| `pcb-edit` 命令入口 | 保留 `ok/status/saved/steps/reportFile`，透传 `assignments/changedCount`；执行成功为 `status: verified` |

Action 各模式均返回 target，入口核对结果的项目/PCB 身份。`assignments` 在预览、执行和命令结果中保持同一结构：`{name, nets, hex, color: {r,g,b,alpha}}`，其中 hex 为大写 `#RRGGBB`，alpha 为回读范围的 1。输入 color 仍是 HEX 字符串，执行输入直接使用 applyRequest。命令预览 changedCount 是预计变化类数，执行成功后是实际变化类数；开始执行后至确认成功前为 null，失败时不把计划数量当成已完成数量。输入校验失败由 runner 返回错误，不视为已执行。

命令默认只预览，即使输入有 save=true 也不写入；`--apply` 执行并保存。直接调用 Action 时 save 默认为 false。命令预览的 saved=null 表示未检查保存状态；执行的 saved 含义见下文。保留本版有效输入和返回字段，内部整理不改变调用约定。

固定配色标准：

| kind | 用途 | 颜色 | HEX |
| --- | --- | --- | --- |

上游根据电路用途提供 kind；不可仅凭 SCL/SDA 字样判断协议，复用管脚以实际功能为准。UART TX/RX 以本项目主控视角命名；多控制器项目由上游明确参照。低有效后缀不会改变用途色。同类信号（如多路 SCL）同色，颜色不承担区分所有网络的任务。

显式 `color: "#RRGGBB"` 优先于 kind，保留项目特例及冻结后的 applyRequest。未定义的 kind 没有有效 color 时在写入前报错，不从类名猜测，也不自动分配候补色；需要新的语义类型时扩充本表和配色核心。可选 nets 必须与已有类完整成员一致；只给 nets 时须唯一匹配已有类。输入错误、重复选择和重叠成员会在写入前停止。

改色沿用已验证的 delete/create 机制：保留原成员，写入 alpha=255，回读必须为 1；恢复重建影响的配置和网络规则，在首个写入前、每类写入后以及保存后回读。规则比较只忽略排列顺序，使用类型和名称区分同名网络/网络类，保留全部规则字段。每次执行使用当前规则，无整板源码指纹和几何扫描。执行期间保持该 PCB 独占编辑；这项验证仅覆盖网络类和规则。

失败立即停止，返回原网络类、规则及已尝试类名，不自动重试或回滚。中断可能留下缺失类，先 inspect 并对照失败报告恢复。saved=true 表示保存接口已确认，false 表示尚未尝试保存，null 表示已尝试但未确认成功；保存后回读仍可能报错。
